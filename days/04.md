# Day 04 of #30daysofawsterraform: S3 Native State Locking – DynamoDB No Longer Needed

Today was a game-changer. I moved my Terraform state to a remote S3 backend, but with a modern twist: **S3 native state locking** using Terraform 1.11+. No DynamoDB table required anymore!

If you've been doing Terraform for a while, you're used to the classic "S3 + DynamoDB" combo. Well, things have evolved. Let me show you the cleaner way.

## Why Remote State? (Quick Recap)

- **Team collaboration** – Everyone reads/writes the same state file
- **Security** – No secrets lying around on laptops
- **Auditability** – Track every infrastructure change

## The New Architecture: S3 Native Locking

Here's what we built today – notice **no DynamoDB** in sight:

```
+----------------+                                   +-------------------------+
|                |   terraform init                  |                         |
|   Your local   | ---------------------------------> |   S3 Bucket             |
|   Terraform    |                                   |  - Versioning enabled   |
|   (v1.11+)     | <-------------------------------- |  - AES-256 encryption   |
|                |   .tflock file (temp)             |  - .tflock files for    |
+----------------+                                   |    state locking        |
                                                     +-------------------------+
                                                              |
                                                              | state + lock files
                                                              v
                                                     +-----------------+
                                                     | terraform.tfstate|
                                                     | terraform.tflock | (temp)
                                                     +-----------------+
```

## Step 1: Create the S3 Backend with a Script

I ran `test.sh` first to set up my bucket. This script does everything:

```bash
#!/bin/bash

BUCKET_NAME="terraform-state-$(date +%s)"
REGION="us-east-1"

# Create S3 bucket for state storage
aws s3 mb s3://$BUCKET_NAME --region $REGION

# Enable versioning on the bucket (REQUIRED for S3 native state locking)
aws s3api put-bucket-versioning \
  --bucket $BUCKET_NAME \
  --versioning-configuration Status=Enabled

# Enable server-side encryption
aws s3api put-bucket-encryption \
  --bucket $BUCKET_NAME \
  --server-side-encryption-configuration '{
    "Rules": [
      {
        "ApplyServerSideEncryptionByDefault": {
          "SSEAlgorithm": "AES256"
        }
      }
    ]
  }'

echo "======================================"
echo "S3 Backend Setup Complete!"
echo "======================================"
echo "Bucket Name: $BUCKET_NAME"
echo "Region: $REGION"
echo "Versioning: Enabled (required for state locking)"
echo "Encryption: Enabled (AES256)"
```

**What this script does:**
- Creates a uniquely named bucket using timestamp
- Turns ON versioning (critical for locking)
- Turns ON AES-256 encryption

## Step 2: Configure Backend in Terraform

My `main.tf` now looks like this – notice the `use_lockfile = true` instead of a DynamoDB table:

```hcl
terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 6.0"
    }
  }

  # S3 backend with native locking (NO DynamoDB needed!)
  backend "s3" {
    bucket        = "terraform-state-1754513244"  # From my script output
    key           = "dev/terraform.tfstate"
    region        = "ca-central-1"
    use_lockfile  = true   # This enables S3 native locking
    encrypt       = true
  }
}

provider "aws" {
  region = "ca-central-1"
}

# Test resource to verify everything works
resource "aws_s3_bucket" "test_backend" {
  bucket = "test-remote-backend-${random_string.bucket_suffix.result}"

  tags = {
    Name        = "Test Backend Bucket"
    Environment = "dev"
  }
}

resource "random_string" "bucket_suffix" {
  length  = 8
  special = false
  upper   = false
}
```

## How S3 Native Locking Works (The Magic)

With `use_lockfile = true`, Terraform now:

1. **Creates a temporary `.tflock` file** in S3 before making changes
2. **Uses S3 Conditional Writes** – only one process can create the lock file
3. **Automatically releases** the lock by deleting the `.tflock` file
4. **No DynamoDB** – S3 does the locking natively

**Why this is better:**
- Simpler setup (one resource instead of two)
- No DynamoDB costs or throughput limits
- Available in Terraform 1.10+, stable in 1.11+

## Good to Know: Security & Versioning

### Why Versioning is Required

S3 native locking **depends on versioning**. Here's why:
- When Terraform creates a `.tflock` file, it uses conditional PUT operations
- Versioning ensures these conditional writes work correctly
- Without versioning, locking fails immediately

### Encryption Protects Your State

Your `terraform.tfstate` contains:
- Resource IDs, ARNs, and dependencies
- Potentially secrets (database passwords, API keys)
- Network topology (VPC IDs, subnet CIDRs)

With `encrypt = true` and bucket encryption enabled:
- Data is encrypted at rest using AES-256
- AWS handles key management automatically
- Authorized users still read/write normally

### Never Commit State to Git

S3 backend replaces Git for state storage. Git is for code, S3 is for state:
- State files can grow to 100MB+
- They change on every `apply` (bad for Git diffs)
- S3 gives you versioning without bloating your repo

## The Big Takeaway

**Old way (still works):** S3 backend + DynamoDB table for locking

**New way (Terraform 1.11+):** S3 backend + `use_lockfile = true`

Less moving parts. Simpler setup. Same reliability.
