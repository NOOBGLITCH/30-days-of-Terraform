## What Are Meta-Arguments?

Meta-arguments live inside any `resource`/`data` block but are handled by Terraform core, not the provider. They change **how** a resource is created, not what it is.

The six we cover today:

| Meta-Argument | What it does |
|---|---|
| `count` | Create N identical copies, indexed `0..N-1` |
| `for_each` | Create one resource per item in a map/set |
| `depends_on` | Force an explicit dependency/ordering |
| `lifecycle` | Tune create/update/destroy behavior |
| `provider` | Use a non-default (aliased) provider config |
| `for` expression | Transform collections (used in outputs/locals) |

---

## 1. `count` — Multiple Identical Resources

`count` turns a single resource block into a list of N identical resources. Each copy is addressed with `count.index`.

```hcl
resource "aws_s3_bucket" "log" {
  count  = var.instance_count
  bucket = "${var.bucket_base_name}-log-${var.environment}-${count.index}"
}
```

Key facts:

- `count.index` is 0-based (`0, 1, 2, ...`).
- The resource becomes a **list**: reference it with `aws_s3_bucket.log[0].id`.
- Changing `count` adds/removes items from the end (Terraform tracks by index).
- Index-based addressing is fragile if you reorder — prefer `for_each` when items have meaningful names.

Best practice: use `count` only when the items are truly interchangeable (e.g., a fixed pool of identical workers).

---

## 2. `for_each` — One Resource Per Map/Set Item

`for_each` is like `count` but each instance has a stable, named key. This makes adds/removes safe because Terraform tracks by key, not position.

```hcl
resource "aws_s3_bucket" "user" {
  for_each = var.users
  bucket   = "${var.bucket_base_name}-${each.key}-${var.environment}"

  tags = {
    Owner = each.key
    Role  = each.value
  }
}
```

Two flavors:

- **Map** → `each.key` and `each.value` are both available.
- **Set** → only `each.key` exists (values are identical). Convert a list with `toset([...])`.

```hcl
resource "aws_s3_bucket" "env" {
  for_each = toset(["dev", "staging", "prod"])
  bucket   = "${var.bucket_base_name}-env-${each.key}"
}
```

Addressing: `aws_s3_bucket.user["alice"].arn`.

Best practice: use `for_each` whenever each item has a meaningful identity (users, environments, regions). It's almost always safer than `count`.

## 3. `depends_on` — Explicit Dependencies

Terraform normally figures out dependencies from references (e.g., `bucket = aws_s3_bucket.x.id`). `depends_on` forces an ordering when there is **no direct reference** but the dependency is still real.

```hcl
resource "aws_s3_bucket_public_access_block" "user_block" {
  for_each                = aws_s3_bucket.user
  bucket                  = each.value.id
  block_public_acls       = true
  block_public_policy     = true
  ignore_public_acls      = true
  restrict_public_buckets = true

  depends_on = [aws_s3_bucket.user]
}
```

Caveats:

- Overusing `depends_on` slows plans and can create cycles. Let implicit references do the work whenever possible.
- `depends_on` with `for_each`/`count` applies to the whole set — use it carefully.

## 4. `provider` — Alternate Provider Configurations

You can declare the same provider multiple times with an `alias` and then point a resource at the alias with the `provider` meta-argument. Common for multi-region or multi-account setups.

```hcl
# provider.tf
provider "aws" {
  alias  = "us_east"
  region = "us-east-1"
}
```

```hcl
resource "aws_s3_bucket" "dr" {
  provider = aws.us_east
  bucket   = "${var.bucket_base_name}-dr-${var.environment}"
}
```

Notes:

- The default provider (no alias) is used automatically; aliased providers must be referenced explicitly.
- An aliased provider must also be declared in `required_providers` indirectly via the base provider.
- Great for DR buckets, replicated data, or managing resources across accounts.

## 5. `lifecycle` — Control Create/Destroy Behavior

`lifecycle` is itself a meta-argument block. Day 09 goes deep on every sub-block, but we use one here:

```hcl
resource "aws_s3_bucket" "important" {
  bucket = "${var.bucket_base_name}-important-${var.environment}"

  lifecycle {
    prevent_destroy = true
  }
}
```

`prevent_destroy = true` makes `terraform destroy` (and any plan that would delete the resource) **fail** instead of deleting — perfect for "do not lose this" resources.

## 6. `for` Expressions — Transform Collections

Technically a language feature (not a resource meta-argument), but it pairs perfectly with `count`/`for_each` to reshape outputs.

```hcl
# list comprehension
output "log_bucket_names" {
  value = [for b in aws_s3_bucket.log : b.bucket]
}

# map comprehension
output "user_bucket_arns" {
  value = { for k, b in aws_s3_bucket.user : k => b.arn }
}

# with a transform
output "user_roles_upper" {
  value = { for name, role in var.users : name => upper(role) }
}
```

Syntax:

- `[for ITEM in COLLECTION : EXPRESSION]` → produces a **list**.
- `{for KEY, VALUE in COLLECTION : NEW_KEY => NEW_VALUE}` → produces a **map**.
- Add `if CONDITION` at the end to filter.

## Best Practices Recap

1. **Prefer `for_each` over `count`** when items have identities.
2. **Use `count`** only for interchangeable, order-based pools.
3. **Avoid `depends_on`** unless Terraform can't infer the dependency.
4. **Alias providers** for multi-region/multi-account, not everyday use.
5. **Use `lifecycle`** to guard critical resources and control churn.
6. **Use `for` expressions** to keep outputs clean and composable.
