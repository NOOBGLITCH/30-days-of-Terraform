# Terraform Lifecycle Meta-Arguments (AWS) — Day 09 of 30 Days of Terraform

On **Day 09** we go deep on the `lifecycle` block. Lifecycle rules tell Terraform **how to handle a resource across create, update, and destroy** — instead of just declaring the desired end state. This is where you prevent outages, protect critical data, and survive real-world drift.

## What Is the `lifecycle` Block?

```hcl
resource "aws_s3_bucket" "example" {
  # ... arguments ...

  lifecycle {
    # lifecycle rules go here
  }
}
```

It contains these rules:

| Rule | Effect |
|---|---|
| `create_before_destroy` | Build the new resource before deleting the old one |
| `prevent_destroy` | Block destroy/replace of this resource |
| `ignore_changes` | Ignore changes to specific arguments |
| `replace_triggered_by` | Replace this resource when another changes |
| `precondition` | Abort **before** create if a check fails |
| `postcondition` | Abort **after** apply if a check fails (outputs only) |

---

## 1. `create_before_destroy` — Zero-Downtime Deployments

By default Terraform **destroys then creates** when a resource must be replaced. With `create_before_destroy = true` it does the opposite: **creates the replacement first, then destroys the old one**. The name (or resource) never goes missing.

```hcl
resource "aws_s3_bucket" "blue_green" {
  bucket = "${var.app_name}-${var.environment}-${var.deploy_version}"

  lifecycle {
    create_before_destroy = true
  }
}
```

When to use it:

- Blue/green or canary deployments.
- Anything where a gap = downtime (load balancers, DNS, buckets behind a name).
- **Most powerful with `count`/`for_each`**: Terraform rolls instances one at a time.

Gotchas:

- The old and new resources must be able to **coexist** (e.g., unique names). That's why the bucket name includes a version label.
- Can't be combined with `prevent_destroy` on the same resource.

## 2. `prevent_destroy` — Protect Critical Resources

```hcl
resource "aws_dynamodb_table" "critical" {
  name         = "${var.app_name}-table-${var.environment}"
  billing_mode = "PAY_PER_REQUEST"
  hash_key     = "id"
  attribute { name = "id" type = "S" }

  lifecycle {
    prevent_destroy = true
  }
}
```

Behavior:

- Any plan that would **destroy or replace** this resource fails with an error instead of proceeding.
- Great guardrail for databases, state buckets, and production data stores.
- It does **not** block in-place updates (changing `billing_mode` is fine) — only deletion/replacement.

Tip: wrap `terraform destroy` in CI and keep `prevent_destroy` on to stop accidental wipes.

## 3. `ignore_changes` — Handle External Modifications

Sometimes another system (or a teammate) legitimately edits a resource outside Terraform — auto-scaling groups resize, external tools tag resources, etc. `ignore_changes` tells Terraform to **not plan changes** to those arguments even if the config differs.

```hcl
resource "aws_instance" "web" {
  ami           = "ami-006f82a1d5a27da54"
  instance_type = var.instance_type

  tags = merge(var.common_tags, { Name = "${var.app_name}-web" })

  lifecycle {
    ignore_changes = [tags]
  }
}
```

Forms:

- `ignore_changes = [tags]` — ignore the whole argument.
- `ignore_changes = [tags["CreatedDate"]]` — ignore a single map element.
- `ignore_changes = all` — ignore everything except arguments still referenced elsewhere (use sparingly).

Best practice: ignore only what's truly externally managed, to avoid silently drifting config.

## 4. `replace_triggered_by` — Dependency-Based Replacement

Sometimes you want Resource B to be **replaced whenever Resource A is replaced**, even if B's own config didn't change. `replace_triggered_by` encodes that coupling.

```hcl
resource "aws_security_group" "web_sg" {
  name = "${var.app_name}-sg"
  # ... ingress/egress ...

  lifecycle {
    replace_triggered_by = [aws_instance.web]
  }
}
```

Notes:

- Takes a **list of resource references**.
- Unlike `depends_on`, this triggers *replacement* (destroy + create), not just ordering.
- Useful for pairs that must stay in lockstep (e.g., a security group "owned" by an instance).

## 5. `precondition` — Pre-Deployment Validation

A `precondition` runs **before** Terraform creates the resource. If `condition` is false, the apply aborts with your `error_message` — no half-built infrastructure.

```hcl
resource "aws_s3_bucket" "deploy" {
  bucket = "${var.app_name}-deploy-${var.environment}"

  lifecycle {
    precondition {
      condition     = length(var.environment) > 0
      error_message = "The environment variable must not be empty."
    }
  }
}
```

Use it to enforce business rules that types can't express (non-empty values, allowed ranges, naming patterns).

---

## 6. `postcondition` — Post-Deployment Validation

A `postcondition` runs **after** a value is known (typically on an `output`). It verifies the real result matches expectations.

```hcl
output "deploy_bucket" {
  value = aws_s3_bucket.deploy.bucket

  lifecycle {
    postcondition {
      condition     = can(regex("^[a-z0-9-]+$", aws_s3_bucket.deploy.bucket))
      error_message = "Bucket name must contain only lowercase letters, numbers, and hyphens."
    }
  }
}
```

Use `precondition`/`postcondition` together for defense-in-depth:

- **precondition** → "don't even start if inputs are wrong."
- **postcondition** → "fail loudly if the result is wrong."

## Connecting the Dots

```
precondition ─────► abort before create (validate inputs)
       │
       ▼
   create resource
       │
       ├─ create_before_destroy ─► new before old (zero downtime)
       ├─ ignore_changes ───────► tolerate external edits
       ├─ replace_triggered_by ─► replace when dependency changes
       ├─ prevent_destroy ──────► never destroy this resource
       │
       ▼
postcondition ────► abort after apply (validate result)
```

---

## Best Practices Recap

1. Use `create_before_destroy` for anything where a gap = downtime.
2. Put `prevent_destroy` on databases and state buckets.
3. Keep `ignore_changes` minimal and documented.
4. Reach for `replace_triggered_by` when two resources must roll together.
5. Add `precondition`/`postcondition` as cheap, powerful validation.
6. Commit `.terraform.lock.hcl` so lifecycle behavior is reproducible.
