# Terraform Data Sources — Day 13 of 30 Days of Terraform

On **Day 13** I learned how to use Terraform **data sources** to reference existing infrastructure instead of creating everything from scratch. Data sources let Terraform read information from the cloud provider — VPCs, subnets, AMIs, and more — and use that information in resource configurations. This is essential for deploying into pre-existing networks and using the latest approved images.

## 1. Data Sources — Reading Existing Infrastructure

A `data` block tells Terraform to **fetch information** from the provider without creating any resources. The result can then be used in resource configurations.

### Fetching an Existing VPC

```hcl
data "aws_vpc" "shared" {
  filter {
    name   = "tag:Name"
    values = ["shared-network-vpc"]
  }
}
```

This queries AWS for a VPC with the tag `Name = "shared-network-vpc"`. The result is stored in `data.aws_vpc.shared` and can be referenced like any resource attribute:

- `data.aws_vpc.shared.id` — The VPC's ID
- `data.aws_vpc.shared.cidr_block` — The VPC's CIDR range
- `data.aws_vpc.shared.tags` — All tags on the VPC

### Fetching an Existing Subnet

```hcl
data "aws_subnet" "shared" {
  filter {
    name   = "tag:Name"
    values = ["shared-primary-subnet"]
  }
  vpc_id = data.aws_vpc.shared.id
}
```

This fetches a subnet within the VPC we just looked up. The `vpc_id` argument scopes the search so we don't accidentally match a subnet with the same name in a different VPC.

Reference the subnet in a resource:

```hcl
resource "aws_instance" "main" {
  subnet_id = data.aws_subnet.shared.id
  # ...
}
```

### Fetching the Latest Amazon Linux 2 AMI

```hcl
data "aws_ami" "amazon_linux_2" {
  most_recent = true
  owners      = ["amazon"]

  filter {
    name   = "name"
    values = ["amzn2-ami-hvm-*-x86_64-gp2"]
  }

  filter {
    name   = "virtualization-type"
    values = ["hvm"]
  }
}
```

This is one of the most common data source patterns. Instead of hard-coding an AMI ID (which becomes stale as AWS updates images), we query for the **latest** Amazon Linux 2 AMI that matches our filters:

- `most_recent = true` — Returns the newest image matching the filters
- `owners = ["amazon"]` — Only images published by Amazon
- Two `filter` blocks — one for the name pattern, one for virtualization type

Reference the AMI in a resource:

```hcl
resource "aws_instance" "main" {
  ami           = data.aws_ami.amazon_linux_2.id
  instance_type = "t3.micro"
  # ...
}
```

## 2. The EC2 Instance — Putting It All Together

With the data sources providing the VPC, subnet, and AMI, the instance resource is straightforward:

```hcl
resource "aws_instance" "main" {
  ami           = data.aws_ami.amazon_linux_2.id
  instance_type = "t3.micro"
  subnet_id     = data.aws_subnet.shared.id
  private_ip    = "10.0.1.50"

  tags = {
    Name = "day13-instance"
  }
}
```

Key points:

- **No provider block** in `main.tf` — the provider is inherited from the root module or a separate `provider.tf` file.
- **`data.aws_ami.amazon_linux_2.id`** — Uses the data source to get the latest AMI ID dynamically.
- **`data.aws_subnet.shared.id`** — Uses the data source to get the existing subnet ID.
- **`private_ip`** — Hard-coded to a specific IP in the subnet's CIDR range.

## 3. The Setup Folder — Simulating Existing Infrastructure

The `setup/` folder contains resources that simulate a pre-existing VPC and subnet. In a real-world scenario, these would already exist in your AWS account — created by another team, another Terraform project, or manually through the console.

### `setup/main.tf`

```hcl
provider "aws" {
  region = "ap-south-1"
}

resource "aws_vpc" "shared" {
  cidr_block = "10.0.0.0/16"
  tags = {
    Name = "shared-network-vpc"
  }
}

resource "aws_subnet" "shared" {
  vpc_id     = aws_vpc.shared.id
  cidr_block = "10.0.1.0/24"
  tags = {
    Name = "shared-primary-subnet"
  }
}
```

### `setup/outputs.tf`

```hcl
output "vpc_id" {
  value = aws_vpc.shared.id
}

output "subnet_id" {
  value = aws_subnet.shared.id
}

output "vpc_name" {
  value = aws_vpc.shared.tags["Name"]
}

output "subnet_name" {
  value = aws_subnet.shared.tags["Name"]
}
```

> **Note:** The `setup/` folder is only needed for local testing. In production, the VPC and subnet already exist and the data sources will find them by their tags.

## Connecting the Dots

```
setup/main.tf ──► Creates VPC + Subnet (for testing only)
                         │
                         ▼
main.tf ──► data "aws_vpc" ──► Finds VPC by tag "shared-network-vpc"
         ──► data "aws_subnet" ──► Finds subnet by tag "shared-primary-subnet"
         ──► data "aws_ami" ──► Finds latest Amazon Linux 2 AMI
                         │
                         ▼
                  aws_instance.main ──► EC2 in the existing subnet
                         │
                         ▼
                  outputs.tf ──► Exposes instance ID and private IP
```

Data sources create a **read-only dependency** on existing infrastructure. Terraform reads the data at plan time and uses it to configure resources, but it never manages the data source resources themselves.

## Best Practices Recap

1. **Use data sources for existing infrastructure** — Never hard-code VPC IDs, subnet IDs, or AMI IDs when they can be fetched dynamically.
2. **Scope data source filters precisely** — Use `vpc_id` on subnet lookups and tag filters on VPC lookups to avoid ambiguous matches.
3. **Use `most_recent = true` for AMI data sources** — Hard-coded AMI IDs become outdated as AWS patches and updates images.
4. **Use tags to identify shared resources** — Tagging VPCs and subnets with predictable names makes data source lookups reliable.
5. **Separate setup resources from production code** — The `setup/` folder simulates existing infrastructure for local testing; remove it before deploying to a real environment.
6. **Data sources are read-only** — Terraform does not manage data source resources. They are fetched at plan time and used as inputs to resource configurations.

## What I Learned

* **Data sources** are `data` blocks that fetch information from the provider without creating any resources — they are read-only references to existing infrastructure.
* **`data "aws_vpc"`** — Queries AWS for a VPC using tag filters. The result can be referenced as `data.aws_vpc.shared.id` and used in resource configurations.
* **`data "aws_subnet"`** — Fetches a specific subnet within a VPC. The `vpc_id` argument scopes the search to avoid ambiguous matches.
* **`data "aws_ami"`** — Queries for the latest Amazon Machine Image matching filters. Using `most_recent = true` avoids hard-coding stale AMI IDs that become outdated as AWS patches images.
* **Data sources create read-only dependencies** — Terraform reads the data at plan time and uses it to configure resources, but it never manages the data source resources themselves.
* **Tag-based lookups** are the standard pattern for finding existing infrastructure — VPCs, subnets, security groups, and other resources can be found by their tags without needing to know their IDs in advance.
* **The `setup/` folder pattern** simulates pre-existing infrastructure for local testing. In production, the VPC and subnet already exist and the data sources find them by tag.
* **`variable.tf` vs `variables.tf`** — This project uses `variable.tf` (singular) instead of the more common `variables.tf` (plural). Both work; the file name doesn't matter to Terraform.
